## 評估方法

- JS／CSS 尺寸以目前工作樹檔案的原始 bytes 計算。
- gzip 使用最高壓縮等級；Brotli 使用 quality 11。兩者均為離線壓縮尺寸估算，不代表特定 CDN 的傳輸封裝。

## H-06-03 候選方案成本／收益／風險矩陣

目前總量基線是 24 個一般頁面資產請求、約 2.12 MB transfer bytes（`derivatives-status.html` 為 25 個請求）；其中 15 個 JS slice＋7 個 CSS split 的 Brotli 離線估算為 379,385 bytes，另加 `pwa.js`／`app.js`。以下為不建置、不改線上設定的方案評估。

| 候選方案 | 預期收益 | 主要成本 | 行為／安全風險 | 評估結論 |
|---|---|---|---|---|
| 維持 classic slices | 零遷移成本；現有 21 頁、24 個一般資產請求的載入順序與 global scope 不變 | 保留 15 JS＋7 CSS 的請求與每頁全量載入；目前 no-store 使 warm cache 無收益 | 最低；可直接沿用既有 21 頁／94 interaction 護欄 | 短期 default；作為回退基線 |
| HTTP/2／HTTP/3 transport tuning | 多路復用可降低多資產 head-of-line／連線建立成本，不需改 JS 模組 | 需確認 hosting／CDN／TLS／protocol 支援與觀測；payload bytes 不會因協定自動消失 | 部署與網路層變更；無法解決 no-store 或全量載入 | 可作平台前置條件；單獨收益不足以立項 |
| 保守 bundler：先合併共用 runtime，再保留 route bundles | 可把請求數從 15 JS slice 降至少數 bundle，跨檔重複壓縮也可能改善；可逐頁載入 | bundler／source map／build reproducibility、watch/debug 流程與 CI 依賴 | classic global symbol、嚴格載入順序、`escapeHtml` 單一來源、CSP 與動態 HTML 依賴最敏感 | 中期首選，但必須 shadow build＋單頁 canary；不在 H-06 執行 |
| CSS 7 split 合併 | 可少 6 個 CSS request；跨 split 壓縮可能略有收益 | cascade 順序、TD-14 split 邊界與 CSS dead-code 重新驗證成本 | selector 覆蓋順序改變可能造成全頁 pixel diff；不能以降低 threshold 掩蓋 | 低優先；需獨立 CSS-only canary |
| preload／cache policy | preload 可能縮短關鍵資產等待；合理 immutable cache 可讓 reload／回訪大幅降 bytes | 需改 response headers／HTML hints／版本化策略與 CDN；preload 全量資產可能增加競爭 | headers、CSP、`CACHE_VERSION`、舊 Service Worker／CDN cache invalidation 失配 | 需與 bundler 或部署批次分開；先做 shadow headers 實驗 |

註：上表第一列的現況資產數應解讀為 **24 個一般資產請求**（15 JS slice、7 CSS split、`pwa.js`、`app.js`）；`derivatives-status.html` 另有 `derivatives-ui.js`。

### 推薦順序

1. 保留 classic slices 作為立即回退路徑。
2. 先做不供應給使用者的 deterministic shadow build，優先驗證 common runtime＋route bundle 是否能維持 global symbol 與載入順序。
3. 通過 H-06-04 canary gate 後，才考慮單頁 bundle；HTTP/2／HTTP/3 與 cache policy 另以部署批次評估，不與 bundler 混合回歸原因。
4. CSS 合併最後處理，並以 CSS-only canary 保護 cascade／pixel diff。

## H-06-04 Canary／回退門檻

本節是未來另立 bundler／部署批次時的執行門檻；H-06 本身不供應 shadow build 產物，也不改現行入口。

### 1. Deterministic shadow build

- 產出與現行 classic slices 平行的 shadow 目錄，不能覆寫 `js/*.js`、`split-*.css`、HTML、baseline 或正式 cache／DB。
- build input、Node／bundler 版本、lockfile、輸出檔名與 source map 必須固定；同一 commit 連續建置兩次，輸出檔名、bytes、hash 必須一致。
- 靜態 gate：所有輸出通過 `node --check`；HTML／CSP 仍只有 `script-src 'self'`，不得出現 `unsafe-inline`／`unsafe-eval`；`escapeHtml` 僅一份；未遺失 895 個既有 global symbol，或由逐項 allowlist 記錄合法封裝變更。
- shadow 只允許被測試 harness 指定載入，不得因建立產物而改變 production request path。失敗時刪除 shadow 產物並回到 classic baseline。

### 2. 單頁 canary

第一個 canary 選 `index.html`（全站入口、P0 互動、涵蓋共用 runtime）；第二個頁面候選為 `futures.html`，只有第一個 canary 全綠才進行。

硬性 gate：

- local JS／CSS／HTML request 無 404、failed request 或 page error；外部字型／資料源錯誤須獨立標示，不得用它們掩蓋 local error。
- screenshot pixel diff ≤ 2%，關鍵 DOM element counts 與 classic baseline 完全一致；`index__penny-trend-market` 代表性互動成功。
- CSP、安全 headers、`escapeHtml` count、global symbol scan 與 API response structure 不退化；不得更新 baseline 來消除未分類差異。

量化 gate（相對本報告的同環境 baseline，至少各 5 次 cold／warm）：p50 first meaningful render proxy 不得退化超過 10%；asset request count 與 transfer bytes 不得增加；候選至少要帶來 15% 以上壓縮後資產減量或至少減少 6 個資產請求，才值得進入全頁 rollout。

### 3. 全頁 rollout gate

- 21／21 頁 frontend compare、94／94 interaction compare、security 16/16、E2E、unit 與所有受影響 JS／Python syntax 全綠。
- 21 頁 local asset error rate 為 0；API／外部失敗依 `[外部問題]` 與 `[程式碼可能改動回應格式]` 分類，後者不得 rollout。
- 重新確認 `docs/frontend_module_map.md` 載入依賴、source map 可追蹤、build manifest 與 release artifact hash；執行 existing／clean package integrity、cache／DB／pycache side-effect hash 檢查。
- 全頁 rollout 必須保留 classic slices 與原 HTML 入口至少一個可立即切換的版本；第一次部署只開 canary 頁，觀測一個完整使用週期後才擴大。

### 4. Revert 路徑

1. 發現任一 hard gate、P0／P1 interaction 或 local asset error 失敗：立即將 feature flag／serving manifest 切回 classic slices，停止擴大流量。
2. 若是 commit／artifact 問題，回退單一 bundler／部署 commit，保留 classic assets；不得回退或覆寫 regression baseline。
3. 若新 bundle 已進 CDN／Service Worker cache，依部署批次預先定義的版本化 key 執行 invalidation；只有在另批次獲確認後才改 `CACHE_VERSION`。
4. 回退後重跑單頁 canary 與 full verify，確認 `VERIFY_OK`；記錄失敗 hash、頁面、request、console 與回退時間，作為下一次 shadow build 的輸入。
