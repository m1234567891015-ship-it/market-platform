# CSS 拆分對照表(styles.css → split-NN.css,根目錄)

## 方法(修訂版,取代最初的語義分組嘗試)

最初嘗試依 `docs/frontend_module_map.md` 第 6 節的 class 前綴統計,把同前綴
規則搬到跟 JS 模組同名的檔案(例如把所有 `chart-`/`asset-finance-` 規則
分別集中到 `css/charts.css`/`css/page-global-market-assethub.css`)。這個
做法在批次 2(`page-global-market-assethub`,598 個規則)的 21 頁 pixel
diff 驗證中,發現 7 個頁面出現 30–50% 的視覺差異——CSS 的 cascade 在同
specificity 時以「目前有效文件順序」決定優先權,同前綴規則抽離、整批搬到
`styles.css` 之前(或之後)載入,會改變它們跟原本交錯在旁邊的通用規則
(例如 `.card`)之間的相對順序,原本靠「剛好排在後面」勝出的規則就會
反過來輸掉。測試「改成搬到 `styles.css` 之後」也只是把失敗頁面換了一批
(5 頁修好、2 頁變壞),證實沒有單一全域載入順序能同時滿足所有衝突。

**現行做法(依使用者裁決,2026-07-25):放棄語意分組,改用純位置切割**——
把 `styles.css` 依原始行號切成連續區段,各自存成獨立檔案,不做任何跨
區段的重新排序或依前綴篩選。所有 `split-NN.css` 依切割順序串接、
再接上 `styles.css` 剩餘內容,等同原始 `styles.css` 逐位元組重現,
cascade 順序因此在建構上就保證 100% 不變(不是靠驗證事後確認沒衝突,
而是切割方式本身就不可能製造衝突)。

**批次 1(`css/charts.css`)因為是舊做法下的語義分組產物,不符合「合併
回來順序必須與原始檔案一致」的新規則,已用 `git revert` 撤銷,連同批次
2 的嘗試一起重做為純位置切割。**

### 額外發現:CSS `url()` 相對路徑必須放在根目錄(不是子目錄)

批次 1 第一次嘗試把切出來的檔案放進 `css/` 子目錄(比照 JS 拆分的 `js/`
慣例),21 頁 pixel diff 抓到全部頁面都有一個新增的 console error
(`Failed to load resource: 404`)。追查後發現:`styles.css` 裡有一條
`background: url("assets/background.jpg") ...`,這種相對路徑的 `url()`
是依「樣式表本身的 URL」解析、不是依頁面 URL。放進 `css/` 子目錄後,
瀏覽器把它解析成 `css/assets/background.jpg`(多一層 `css/`)而 404。

因為修法必須是「零編輯、逐位元組不變」,不能為了修這一條參照去改寫
CSS 內容本身,所以改成讓切出來的檔案**直接放在專案根目錄**(跟
`styles.css` 同一層),不使用子目錄——這樣檔案本身的 URL 目錄層級跟
原本完全一樣,`url()` 相對路徑解析結果不變,不需要碰任何 CSS 內容。
命名維持 `split-01.css`...`split-07.css`(根目錄檔名,不是
`css/split-01.css`),透過既有的 `ROOT_STATIC_FILES`/`static_files`
機制提供(比照 `styles.css` 本身的作法),不需要另外建立 `/css/` 路由
或白名單集合。

### 安全性質

- **切割單位**:以 `regression/slice_css_batch.py` 的 `parse_blocks()`
  找出目前 `styles.css` 的頂層區塊(規則/at-rule/註解)清單,永遠只切
  「從檔案開頭數過來的前 N 個區塊」,不做任何篩選或排序——保證切點
  落在區塊邊界(不會把一條規則切一半、造成語法錯誤),也保證區段內部
  順序、跨區段順序都跟原始檔案完全一致。
- **逐位元組驗證**:每批切割後,直接比對「該批目標檔案內容」是否等於
  搬移前 `styles.css`(指定 git ref)對應行號區間的原始位元組,完全相同
  才算過。
- **重組驗證**:每批也驗證「該批之前所有 `split-*.css` 依序串接 +
  目前 `styles.css`」逐位元組等於原始(修改前)`styles.css`,確保沒有
  遺漏或重複任何內容。
- **驗收標準**:每批 `verify --full` 的 21 頁 pixel diff 必須是零差異
  (不是門檻內的小差異,是零)。任何非零差異視為切割工具本身有 bug
  (例如誤切、順序算錯),要修正切割邏輯本身,不得調整驗收基準來讓
  它通過。
- **未使用規則**:依工單第 8 節,只掃描產報告,不在這個拆分過程中
  刪除任何規則,即使看起來像死碼。
- **載入順序**:`split-01.css` ... `split-07.css` 依序插入
  `<link>` 標籤,全部在 `styles.css` 的 `<link>` 標籤之前,`styles.css`
  隨批次進行持續縮小,最終批次完成後 `styles.css` 清空為止(跟 JS 側
  app.js 最終留下空殼的收尾方式一致)。
