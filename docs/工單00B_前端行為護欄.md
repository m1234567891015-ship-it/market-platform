# 工單 00-B:前端行為護欄

**類型**:行為不變型(僅新增測試基礎設施,不修改任何應用程式碼)
**前置**:工單 00 已完成、TD-01 / 速贏包 / TD-05+12 已結案
**目的**:在 TD-02(app.js 34,149 行)與 TD-14(styles.css 21,972 行)拆分之前,把既有的 Playwright 從「截圖工具」升級為「互動行為驗證器」,補上目前護欄唯一的缺口。

---

## 0. 為何需要這張工單

現有護欄的實際覆蓋:

| 面向 | 機制 | 狀態 |
|---|---|---|
| 資料導入 | 48 端點 API golden file 逐欄比對 | 已有 |
| 後端邏輯 | 94 個 unit test + 五層驗證 | 已有 |
| 後端架構 | registry 不變量測試 | 已有 |
| 頁面初始外觀 | 21 頁 pixel diff | 已有 |
| 頁面載入健康 | console error 零容忍 | 已有 |
| **前端互動行為** | **無** | **本工單補齊** |

缺口的具體形態:以下情況目前**全部**會通過五層驗證而不被發現——

- 圖表週期切換(日K/週K/月K)點了不重繪
- 搜尋框輸入股號後無反應或結果錯誤
- 類股 / 商品下拉選單切換後資料未更新
- 表格排序、分頁按鈕失效
- 分頁籤(tab)切換後內容未載入
- 事件監聽器在重構後未綁定(DOM 靜態時看不出來)

TD-02 要拆的正是這些互動邏輯的本體(`renderStockDetail` 2,376 行為渲染 + 事件綁定 + 資料處理的混合體)。沒有本工單,TD-02 等同無護欄手術。

## 1. 第一部分:互動路徑盤點(必須先做,不可跳過)

**要求**:不得憑猜測設計測試,必須從程式碼實證盤點。

1. 掃描 21 個 HTML 頁面與 app.js,列出所有互動控制項:
   - `addEventListener` 綁定的元素(click / change / input / submit)
   - `onclick` 等 inline handler
   - form、select、input[type=search]、可排序表頭、分頁控制項
2. 產出 `regression/interaction_inventory.md`,逐頁列出:
   - 頁面 → 控制項選擇器 → 觸發事件 → 預期影響的 DOM 區塊
3. 依「使用者實際會做」的重要性分級:
   - **P0(必測)**:該頁的核心功能路徑,壞了等於該頁廢掉
   - **P1(應測)**:次要但常用
   - **P2(選測)**:邊緣功能
4. 盤點結果先回報,經確認後才進入第二部分。

**範圍下限**:每頁至少 1 條 P0 路徑,21 頁合計不少於 25 條 P0。

## 2. 第二部分:互動測試框架

建立 `regression/interaction_check.py`:

1. **沿用工單 00 既有資產**:HAR 錄製 / 重播機制(確保資料不隨行情波動)、既有 Playwright 啟動設定。
2. 每條測試路徑的結構固定為:
   ```
   載入頁面 → 等待就緒 → 記錄操作前的目標 DOM 狀態
   → 執行互動(click / select / type)→ 等待結果
   → 斷言操作後 DOM 狀態
   ```
3. **斷言必須是實質的**,禁止只斷言「沒有 console error」:
   - 目標容器內容確實改變(操作前後不相等)
   - 關鍵元素存在且非空(表格有列、圖表 canvas/svg 有繪製、數值欄位有值)
   - 若該互動觸發 API 請求,斷言請求確實發出且回應被套用
4. 等待策略使用明確條件(元素出現 / 內容變更),禁止使用固定 `sleep` 作為主要同步手段。

## 3. 第三部分:建立基準並凍結

1. 在**目前的 master(TD-05 結案狀態)** 上執行全部路徑,產出:
   ```
   regression/baseline/interactions/
   ├── manifest.json      ← 路徑清單、選擇器、斷言定義
   └── results.json       ← 各路徑的基準通過狀態與關鍵 DOM 摘要
   ```
2. **基準凍結原則**(同工單 00):日後比對失敗一律修程式碼,不得修改基準。唯一例外:該次工單的目標本身就是變更此互動行為,且經人工確認後,以獨立 commit 更新基準並在 message 說明原因。
3. 連續執行 3 次全綠才算基準穩定(防止偶發性 flaky 測試混入基準)。

## 5. 驗收標準

| # | 標準 | 判定 |
|---|---|---|
| 1 | 盤點完整性 | `interaction_inventory.md` 涵蓋 21 頁,P0 路徑 ≥ 25 條,經人工確認 |
| 2 | 自我一致性 | 現行 master 上連續 3 次 `--interactions` 全綠 |
| 3 | **有效性(錯誤注入)** | 見下方,必做 |
| 4 | 整合完成 | `--full` 含互動測試並全綠;`--quick` 時間未顯著增加 |

**驗收 3 的執行方式**(比照工單 00 驗收 2):

隨機挑選 3 條 P0 路徑,分別以下列方式注入故障,確認測試**確實抓到 fail**,再還原:

1. 註解掉某個 `addEventListener` 綁定 → 對應路徑應 fail
2. 讓某個渲染函式提早 `return` → 對應路徑應 fail
3. 破壞某個 DOM 元素的 id/class → 對應路徑應 fail

三種注入若有任何一種未被抓到,代表該路徑的斷言過弱,必須加強後重測。
