# 工單 TD-16:修復法人交易歷史無限遞迴（stack overflow）

**類型**:行為變更型（修復當機路徑）—— 依協作規則，須先提修復方案經確認後才動工
**嚴重度**:高（唯一的使用者可觸發當機級 bug）
**前置**:TD-02 已結案；本輪已建立 `pre-td15-18` git tag 作為回退錨點
**範圍**:`js/stock-detail.js` 的 `loadInstitutionalTradeHistoryIfNeeded` 及其相關呼叫鏈

## 0. 問題描述

`loadInstitutionalTradeHistoryIfNeeded`（原 app.js，現於 `js/stock-detail.js`）在法人交易歷史筆數 < 5 時進入無限遞迴，導致 stack overflow、個股頁籌碼分頁整頁當掉。

此 bug 於工單 00-B 盤點時發現，目前在三處被標記為 known-broken 並排除於互動基準之外:
- `regression/interaction_specs.py` 的 `TW_STOCK_SEARCH.known_issues`
- `regression/interaction_inventory.md`（約 273-280 行）
- `regression/baseline/interactions/manifest.json`（約 833 行）

**注意**:此 bug 是 TD-02 之前就存在的既有問題，TD-02 原樣搬移未修。修復它是行為變更（從「當機」變成「正常顯示」），不是行為不變的重構。

---

## 1. 硬性規則

1. **先重現，後修復**。動任何修復程式碼之前，先寫一條測試證明當機確實發生（見第 2 節），確認測試抓得到，才進行修復。
2. **不擴大範圍**。只修這個遞迴 bug，不順手重構 `renderStockDetail` 或其他 stock-detail 內部邏輯。發現其他問題記錄不修。
3. **修復方案先經確認**。完成第 2 節（重現 + 根因分析）後停下，提出修復方案與影響範圍給我，確認後才進第 3 節。
4. **不得以「跳過」偽裝成修復**。若最終決定短路（<5 筆時不載入歷史），必須是產品行為上正確的決定並明確標示，而非為了讓測試過而讓功能靜默消失。

2. **根因分析**:貼出 `loadInstitutionalTradeHistoryIfNeeded` 的實際遞迴路徑——它在什麼條件下呼叫自己（或間接透過哪個函式繞回自己）、為什麼 < 5 筆時終止條件失效。用實際行號與程式碼說明，不用臆測。
3. **確認觸發邊界**:< 5 是哪個常數或比較式決定的？剛好 5 筆、0 筆、null / 空陣列 各自是什麼行為？列出完整邊界。
