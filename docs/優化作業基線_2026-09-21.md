# Market Pulse 優化作業基線

版本：Baseline-2026-09-21
狀態：已授權凍結
用途：作為後續優化工作的範圍、優先級、驗收與回退依據

## 1. 基線結論

目前專案的核心後端模組化、安全護欄、回歸驗證與部署文件基礎良好。下一階段優化以「穩定性、部署可信度、外部資料源可用性與可維護性」為主，不以大規模重構或新增產品功能為首要目標。

本基線凍結後，任何會改變使用者可見行為、API 契約、部署拓撲、驗證護欄或 baseline/golden files 的工作，均須另案說明方案、影響範圍、驗收方式與回退路徑。

## 2. 已確認的優化起點

### 2.1 立即風險

- `README.md` 含有未清理的 merge conflict 標記。
- 文件宣稱存在 `v1.0-refactor-complete` tag，但目前 repository tag 狀態需重新確認並與文件一致化。
- `render.yaml` 使用 `/tmp` 儲存 cache 與 SQLite；部署文件則描述 `/var/data` persistent disk，設定與文件不一致。
- 測試數量在不同文件中出現 24、115、185 等版本，文件存在狀態漂移。

### 2.2 已知可用性風險

過往檢驗曾記錄下列路徑出現 HTTP 500/502，必須在可連線的 staging/CI 環境重新確認：

- `/twse-data.js`
- Stock search API
- `/api/twse/site-data`
- `/api/twse/live-sectors`
- `/api/twse/live-overview`
- `/api/twse/live-stocks`

TWSE、TAIFEX、Yahoo 等外部資料源的失敗，必須與自身程式錯誤分開標示，不能只以空畫面或一般錯誤回應呈現。

### 2.3 架構限制

目前 rate limit、cache 與 in-flight lock 仍有 process-local 狀態，因此 production 維持單 worker 是既定安全契約。Redis/shared-state 與多 worker rollout 尚未視為完成。

前端 ESM 已具備 loader、bridge、fallback 與 rollback 基礎，但 classic source、bundle、source map 與 fallback 資產暫時視為 production safety net，不得在未取得獨立授權前刪除。

## 3. 凍結的優先級

### P0：交付與部署一致性

1. 清理 `README.md` merge conflict 標記。
2. 統一 Render persistent disk 路徑與部署文件；確認 production 不會因使用 `/tmp` 而遺失資料。
3. 統一測試結果與版本文件，避免手動數字與實際測試漂移。
4. 核對 release tag、release proof 與文件敘述。

### P0：核心 API 可用性

1. 在允許外部 HTTPS 的環境重新執行 `portable_check.py`。
2. 執行 `python regression/verify_against_baseline.py --full`。
3. 對 500/502 路徑取得 server traceback、資料源狀態、timeout 與 fallback 證據。
4. 將外部資料源故障與程式錯誤分成可觀測、可測試的結果。

### P1：測試與資料源降級

1. 建立 PR 必跑的 Python/JavaScript syntax、unit、security、E2E smoke 與 quick baseline gate。
2. 為 Stock search、site-data 與 live endpoints 建立固定離線 fixtures/contract tests。
3. 統一資料源狀態：`healthy`、`stale`、`temporarily_unavailable`、`invalid_payload`。
4. 前端顯示資料時間與來源狀態，避免外部故障被誤判為空資料或前端故障。

### P2：可擴展性與前端收斂

1. 完成正式 staging Redis、雙 worker consistency、斷線策略、backup/restore 與觀測證據後，才評估多 worker。
2. 為 ESM legacy 資產建立移除條件、觀測期與回退演練，不以檔案數量作為完成標準。
3. 持續補強高風險 builder/fetcher 的正常、空資料、格式錯誤、timeout 與上游失敗測試。

## 4. 不在本次基線授權內

- 不新增產品功能。
- 不修改 API response schema 或既有使用者可見行為。
- 不修改 regression baseline、golden files、截圖基準或 interaction manifest。
- 不刪除 classic frontend source、bundle、source map 或 rollback 資產。
- 不增加 production Gunicorn worker 數。
- 不繞過 CSP、XSS、SQL parameterization、SSL production gating 或安全標頭護欄。
- 不順手處理未列入本基線的技術債；發現者應另行記錄。

## 5. 每一項優化的完成門檻

每個優化項目必須具備：

1. 清楚的單一任務範圍與獨立 commit。
2. 變更前後的驗證證據。
3. 不影響既有 API、DOM、CSP、安全標頭與外部錯誤契約的證明；若目標本身是行為變更，須先建立獨立方案與新基準。
4. 可操作的回退路徑。

程式或部署設定有變更時，commit 前必須依 `AGENTS.md` 執行完整六層驗證：syntax、unit、security guardrail、E2E smoke、full baseline，以及適用的逐位元組/搬移驗證。

## 6. 建議執行順序

```text
P0 文件與部署一致性
  → P0 API/外部資料源可用性確認
  → P1 PR CI 與離線 contract fixtures
  → P1 資料源狀態與降級 UX
  → P2 Redis staging 與多 worker 評估
  → P2 ESM legacy 資產移除評估
```

## 7. 基線維護規則

本文件是此次優化作業的基線，不是完成報告。完成項目應在本文件下方新增日期化紀錄，或建立獨立 evidence 文件並連結回來；不得直接改寫既有結論以掩蓋歷史狀態。

任何基線調整都必須說明：調整原因、受影響範圍、是否涉及行為變更、驗證結果與回退方式。
