# 新功能開發規範

> 適用對象:任何在本專案開發**新功能**的人或 AI 代理（Codex 等）。
> 核心問題:本專案的四層護欄是為「重構（行為不變）」設計的，它擅長抓「你改壞了舊東西」，但**對新功能是盲的**——新 API 沒有 golden file、新頁面沒有截圖與互動基準，護欄不會驗證它們是否正確。
> 本規範的目的:**讓每一個新功能在被加入的同一時間，就被納入護欄。** 否則功能會越來越多、護欄卻停在原地，新功能全在網子外裸奔。

---

## 0. 一句話原則

**功能與它的護欄，必須在同一個工作批次內一起交付。不接受「先加功能、之後再補測試」。**

---

## 1. 為什麼這條原則不能妥協

回顧本專案:重構期曾發生「6 頁互動基準靜默遺失」的事故——護欄破了洞，整個前端拆分在破網上進行了很久才被偶然發現。那次的教訓催生了「基準完整性斷言」。

新功能的風險是同一件事的另一面:如果加功能時不同步擴充護欄，等於**主動製造護欄的洞**。三個月後你會有一堆功能，但 `verify --full` 還停在今天的 49 條路由、94 條互動——新功能對護欄完全隱形，任何後續改動弄壞它們都不會報警。

---

## 2. 新功能的分類與對應護欄動作

先判斷你的新功能屬於哪一類，再對照要補的護欄:

### 類型 A:新增 API 端點

**護欄動作(缺一不可):**
1. 在 `regression/baseline/manifest.json` 新增此端點的定義。
2. 執行 capture 產生它的 golden file（回應結構基準）。若回應含時變欄位（價格、時間戳、排名），比照既有端點加遮罩規則。
3. 判斷它屬 `--quick`（有快取層）還是 `--api-live`（設計上永遠即時）——放對旗標分組（見 TD-17 的分類邏輯）。
4. 若端點有多種參數分支，每個代表性分支都要有 golden file。
5. 補對應的 unit test（至少涵蓋正常回應 + 一個錯誤/邊界情況）。

**驗收**:`verify --full` 的端點計數增加、新端點在對的旗標下被比對。

### 類型 B:新增頁面

**護欄動作:**
1. 在 `frontend_check.py` 的頁面清單註冊新頁面 → 產生截圖基準。
2. 在 `interaction_specs.py` 的 `PAGES` 註冊新頁面。
3. 為新頁面的核心功能路徑補**互動測試**（至少 1 條 P0:載入後關鍵容器有內容，或主要互動點擊後 DOM 正確反應）。斷言必須是實質的（見第 4 節），不准只斷言「沒有 console error」。
4. 若新頁面有新的 `js/*.js` 檔:加入 21 頁 HTML 的 `<script>` 載入順序、加入 `JS_MODULE_STATIC_FILES` 白名單（漏加會全頁 404）。
5. **確認基準完整性斷言仍通過**:specs 頁數 == manifest 頁數 == HAR 檔數。新頁面要讓這三個數字同步 +1。

**驗收**:新頁面納入截圖 + 互動基準；完整性斷言三方一致。

### 類型 C:修改既有頁面（加按鈕、加區塊、改版面）

**這一類最需要小心，因為它會讓現有護欄「合理地」紅燈:**
1. pixel diff **會**紅燈（畫面變了）——這是**預期的**。不要為了消紅燈而改到別的地方。
2. 目視確認新版面正確後，**更新該頁截圖基準**，commit message 明確註明「新功能造成的預期畫面變更，非回歸」。這是基準凍結原則的合法例外。
3. 若新增了互動元件（按鈕、下拉、分頁）→ 補對應互動測試路徑，基準互動數 +N。
4. **既有的其他互動路徑必須維持全綠**——確認你只增加、沒改壞旁邊的東西。

**驗收**:截圖基準更新且有說明；新互動路徑納入;既有路徑不變。

### 類型 D:新增後端邏輯（新 builder / 新 fetcher / 新計算）

1. 新 fetcher → 優先評估能否用 `fetch_registry.py` 的宣告式方式（URL/headers/parser/TTL），而非複製樣板（避免重蹈 19.5% 重複的覆轍）。
2. 補 unit test:正常 + 邊界 + 錯誤路徑。
3. 若被某 API 端點使用 → 該端點的 golden file 要涵蓋新邏輯的輸出。

---

## 3. 新功能的標準工作流程

```
1. 提方案:說明功能、影響範圍、屬於類型 A/B/C/D、要補哪些護欄、revert 路徑
   → 等人確認（AGENTS.md 第 5 節:新功能屬行為變更型，須先確認）
2. 實作功能本體
3. 同批次補齊對應護欄（第 2 節）
4. 六層驗證全綠（AGENTS.md 第 4 節）
5. 確認基準完整性斷言通過（頁數/端點數三方一致）
6. 單一功能一個 commit（或功能 + 護欄兩個緊鄰 commit），message 說明
7. 人工檢查點:實際操作新功能一次，確認可用
```

---

## 4. 護欄品質底線（不准偷工）

擴充護欄時，最常見的偷懶是寫「空斷言」讓數字好看但實際沒測到東西。禁止:

- ❌ 互動測試只斷言「沒有 console error」——必須斷言目標 DOM 有實質改變（表格有列、卡片有數值、圖表有繪製、切換後內容變化）
- ❌ golden file 只存最終輸出摘要——要能反映解析邏輯，否則解析改壞了也驗不出來
- ❌ 為了讓 pixel diff 過而降低 threshold——threshold 維持 >2% fail
- ❌ 把 flaky（hover/wheel/drag 類、時序不穩）路徑硬塞進基準——寧可不收，也不要收會偶爾紅燈的路徑（會侵蝕「紅燈=真的壞了」的可信度）

**自我檢查（比照 TD-00B 的錯誤注入驗收）**:新加的護欄，故意把功能弄壞一下（拔掉事件綁定 / 讓函式提早 return / 改壞回應欄位），確認護欄**真的會紅燈**。抓不到就代表斷言太弱，加強後重測。

---

## 5. 每個新功能的完成檢查清單

交付前逐項確認:

- [ ] 功能方案已經人確認
- [ ] 功能本體實作完成，最小 diff
- [ ] 安全不變量未退化（SQL 參數化 / escapeHtml / CSP / 安全標頭）
- [ ] 對應護欄已補（依類型 A/B/C/D）
- [ ] 新護欄通過「錯誤注入」自我驗證（弄壞功能會紅燈）
- [ ] 六層驗證全綠
- [ ] 基準完整性斷言通過（頁數/端點/HAR 三方一致）
- [ ] 若改基準:commit message 說明「預期變更，非回歸」
- [ ] 人工操作新功能一次，確認可用
- [ ] 獨立、語意清楚的 commit

## 6. 掛帳中、與新功能相關的既有債（開發時留意）

- **TD-03**:多 worker 下狀態不共享 → 若新功能引入新的模組層可變狀態，同樣有多 worker 問題，優先考慮放 SQLite/快取層而非模組層 dict。
- **TD-18**:尚無打包 → 新增 js 檔會讓每頁載入量再增加。功能優先，但心裡有數。
- **TD-19**:`schema_diff` 容忍 key 增減 → 新端點若有「關鍵欄位絕不可缺」的需求，別只靠 golden file，考慮補明確的欄位存在性斷言。
