## 1. 硬性規則

1. **刪除清單先經確認**。每一層產出候選清單後停下，經我逐層確認才刪。禁止未確認即刪。
2. **三重證據才准列入刪除**（見第 2 節），任一項證據不足即降級到「標記觀察」，不刪。
3. **分批刪除**，每批不超過 20 個符號 / 規則，每批獨立 commit + `verify --full`。
4. **只刪不改**。刪除死碼的同時不得重構、重命名、移動任何存活的程式碼。
5. **不碰第二層與 CSS 動態類**。這兩批本輪只標記，不刪除。
6. 發現任何非死碼問題（如某個「死碼」其實是被註解掉的功能、或揭露另一個 bug），記錄不修，留獨立工單。

## 2. 刪除的三重證據標準（第一層 JS）

一個 JS 符號要列入「可刪除」，必須同時滿足三項，缺一即降級到第二層（標記觀察）:

1. **AST 可達性**:從 21 頁的任何進入點做靜態可達性分析，確認不可達（沿用 TD-02 盤點所用的 acorn 分析）。
2. **字串掃描**:函式/符號名在**整個 repo** 做純文字搜尋（含所有 `.html` 的 inline handler 與 `data-*`、所有 `.js`、所有 `.css`、所有測試檔、所有 `.py`），確認連字串形式都不出現。這一項專門攔截 `window[name]`、`el.setAttribute("onclick", name+"()")`、字串組函式名這類 AST 抓不到的動態呼叫。
3. **動態呼叫模式排除**:確認該符號所在檔案/模組中，沒有 `window[...]`、`this[...]`、`obj[variable]`、`eval`、`new Function`、`setAttribute("on...")` 等會以變數取用符號的模式指向它。

**三項全過 → 第一層（可刪）。任一項存疑 → 第二層（標記觀察，本輪不刪）。**

## 3. 執行流程

### 第一部分:分類（先做,做完停下回報）

1. 對 98 個 JS 符號逐一套用第 2 節三重證據，產出分類表:
   ```
   docs/td15_js_classification.md
   欄位: 符號名 | 所在檔案:行號 | AST可達性 | 字串掃描結果 | 動態模式 | 判定(第一層/第二層) | 依據
   ```
2. 對 CSS 候選,分出「靜態死碼（可刪）」與「動態組合類（不刪）」:
   ```
   docs/td15_css_classification.md
   欄位: 選擇器 | 出現於哪個 split-NN.css:行號 | 靜態引用掃描結果 | 是否動態拼接 | 判定 | 依據
   ```
   動態拼接判定方式:掃描所有 JS 是否有以字串拼接產生 class 名的模式（例如 `` `sector-${x}` ``、`'is-' + state`、`classList.add(prefix + ...)`）,凡可能命中該 class 的一律歸為動態類、不刪。
3. **分類完成後停下回報**,提交兩份分類表等我確認。我確認後才進第二部分。

### 第二部分:第一層 JS 刪除（確認後執行）

1. 依確認清單分批刪除（每批 ≤ 20 符號）。
2. 每批:刪除 → `node --check` → 六層驗證 → 獨立 commit。
3. `legacy-unclassified.js` 若某批後變空,該檔一併移除,並從 21 頁 HTML 的 `<script>` 標籤與 `JS_MODULE_STATIC_FILES` 白名單移除。

### 第三部分:第二層標記（不刪除）

1. 第二層符號留在原檔,加註標準化標記:
   ```js
   // @TD-15-OBSERVE (2026-07-XX): AST-unreachable but dynamic-call not excluded. Do not delete until observation window clears.
   ```
2. 若專案有部署/測試環境,可選:在這些符號入口加一行 `console.warn("[TD-15-OBSERVE] <name> was called")`,用於觀察期偵測意外呼叫。**此為行為變更（新增 log），需你確認後才加**;不確認則僅加註解。
3. 產出 `docs/td15_observe_list.md`,列出所有第二層符號與標記日期,供下一輪回收。

### 第四部分:第三層 CSS 靜態刪除（確認後執行）

1. 依確認清單分批刪除靜態死 class/ID（每批 ≤ 20 規則）。
2. 每批:刪除 → 六層驗證,**特別確認 21 頁 pixel diff 零差異**（CSS 刪除的主護欄）。
3. **pixel diff 的侷限性提醒**:截圖基準只涵蓋頁面載入後的預設狀態,無法保證涵蓋所有資料狀態（如漲/跌變色、警示標記）。因此即使某 class 靜態掃描為死、pixel diff 也通過,若該 class 名稱語義上關聯到某種資料狀態（如 `-up`/`-down`/`-alert`/`-warning`）,一律降級為不刪、歸入動態觀察類。
